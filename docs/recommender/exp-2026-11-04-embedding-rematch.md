# 실험: 임베딩 모델 재대결 + 입력 텍스트 변형 (2026-11-04 밤 ~ 11-05 아침)

10/15 비교(OpenAI 3-small · BGE-M3 · KURE, 회사 300곳)는 잡음 수준 표본이었고 그 뒤 나온 모델이 있다. 회사 3,000곳(실제 n 1,193~2,101) × 3시점으로
다시 쟀고, 모델과 별개로 "무슨 글을 벡터로 만드느냐"도 한 축으로 봤다. 운영은 건드리지 않았다(하네스 `--embeddings` 로 벡터만 바꿔 끼움).

## 방법
- 하네스: `jobs.evaluate_recommender --companies 3000 --seed 7 --space openai --retrieval hybrid+prd --embeddings <npz>` — 활성 공고 집합은
  `embedding is not null`(OpenAI 열, 2026-10 이전 전수) 이라 세 시점 모두 같은 공고 풀. 회사 벡터 합성·자격·점수·MMR 은 운영과 동일.
- 텍스트: `docs/recommender/scripts/export_embed_texts2.py`(시점 t 로 복원한 프로필 — 하네스와 같아야 업종 텍스트가 맞는다) → 네 변형을 한 번에.
- 임베딩: `docs/recommender/scripts/embed_models.py`. GPU 모델은 fp16·max_seq 512·L2. 지시문이 필요한 모델(Qwen3·E5·Arctic)은 질의 쪽(업종 텍스트)에만
  접두어. Gemini 는 문서 `RETRIEVAL_DOCUMENT` / 질의 `RETRIEVAL_QUERY` 비대칭, 3072d. OpenAI 는 text-embedding-3-large 3072d.
- 오케스트레이션: 임베딩(GPU 직렬·API 병렬) → 채점표 동시 4개. 채점표 한 번 12~23분. 밤새 총 50여 회.
- 지표는 `r_final20`(운영 화면 20건 안에 낙찰 공고) 를 기준으로 보고, dense(후보 회수)·f5·MRR·군별을 같이 본다. 판단 규칙은 CLAUDE.md 그대로 —
  세 시점 같은 방향, cold/small/rich 어느 군도 떨어지지 않을 것.

- **차원은 768 로 줄여도 된다.** MRL 축소 세 단계가 전부 잡음 안이고 768 이 오히려 최고다. 운영은 `vector(768)` + 일반 HNSW 로 충분(halfvec 불필요), 저장은 KURE 1024d 보다 작다.
- **글은 운영 그대로.** 모델을 바꿔도 "항목명 7줄 + 수요기관" 이 제일 낫다. 첨부 요약은 Gemini 에서도 득이 없다.
- **taskType 을 꼭 나눠 써야 한다.** 공고는 `RETRIEVAL_DOCUMENT`, 업종 텍스트·키워드 질의는 `RETRIEVAL_QUERY`. 같은 과제형으로 넣으면 KURE 와 비슷한 수준으로 내려앉는다.
  회사 벡터 = 업종 텍스트(질의) + 이력 공고(문서) 가중합이라 두 종류가 섞이는데, 그 상태로 측정한 결과가 위 표다.
- **10/1 시험 시점(한 번만)**: Gemini 3072d final@20 **0.696** vs KURE **0.640** (+0.056), dense 0.845 vs 0.762, cold +0.05 / small +0.06 / rich +0.06. 7/1·8/1·9/1 에서 고른 것이 처음 보는 시점에서도 유지된다. (768d 10/1 은 아래 추가 실험)

## 점수표 재적합 (Gemini 특징, 8/1 적합 → 9/1·7/1 검증)
`--dump-features` 3시점 → `fit_score_weights`. 적합된 표는 기관 +12→+5, 지역 +9→+5, 허용업종존재 0→−5, 나머지 0. 자격 통과 풀 안에서 r30 는 검증 시점에서 +0.006/+0.025 오르지만
**r5 는 −0.048/−0.052, MRR −0.035/−0.034** 로 상위가 무너진다. 10/15 KURE 때와 같은 결론 — **점수표는 현재 표 유지.** (Gemini 유사도 분포에 맞는 배율 k 만 `sweep_score_scale` 로 훑는 건 전환 때 할 일.)

## 운영에 넣으려면 (결정 대기)
- **권장안: Gemini embedding-001, `outputDimensionality=768`, 공고 `RETRIEVAL_DOCUMENT` / 질의 `RETRIEVAL_QUERY`, 글은 운영 그대로, 점수표 유지.**
- pgvector 0.8.2 — 768d 는 일반 `vector` HNSW 로 된다(3072d 를 그대로 쓰려면 `halfvec`, 불필요).
- 비용: Gemini embedding-001 유료 $0.15/M 토큰. 하루 신규 공고 ~1.5천 + 회사 텍스트 ~3천 + 키워드 질의 ≈ 0.5M 토큰/일 ≈ **$0.07/일**. 무료 등급은 분당 한도가 낮아
  배치(하루 수천 건)와 요청 시점 질의를 같이 돌리기엔 좁다 — **결제 등록 필요**. 이번 실험 중 7개 병렬 임베딩이 429 로 멈췄고, 한 번에 하나씩은 통과했다.
- 상주 모델이 사라진다: Railway 의 409MB ONNX·기동 다운로드·메모리 1GB 가 없어지고 키워드 질의는 API 왕복(~200ms). 그러면 백엔드를 어디 두느냐의
  선택지가 넓어진다(Cloudflare 포함).
- 전환 작업: 벡터 열 신설(bid_notices·companies·pre_specs·order_plans, halfvec 또는 1536d) + RPC `_g` 변형 + `EMBED_SPACE=gemini` + 전수 재임베딩
  (활성 공고 ~1만 + 이력 공고 + 회사 7.8만 — API 로 수십 분) + 점수표 재적합(`fit_score_weights`, Gemini 유사도 분포) + 채점표 전후 비교 → 배포. 롤백은 `EMBED_SPACE`.
- 외부 의존: 구글 API 장애 때 키워드 모드만 영향(회사 모드는 벡터 사전계산). 임베딩 캐시(0046)가 재시도 비용을 막는다.
- 한계: 하네스는 회사 모드만 잰다. 키워드 모드(자유 텍스트 질의)는 `RETRIEVAL_QUERY` 로 같은 공간에 들어가지만 별도 측정이 없다 — 전환 뒤 키워드 질의 상위 20건을
  KURE 와 나란히 보는 블라인드 비교를 한 번 한다. 또 10/1 시험은 한 번만 쓴 상태다.
