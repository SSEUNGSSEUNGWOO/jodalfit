# 실험: 임베딩 모델 비교 — OpenAI text-embedding-3-small vs BGE-M3 vs KURE-v1 (2026-10-15)

후보 검색 손실(낙찰 공고가 dense 후보 400 밖)이 가장 큰 병목이라 임베딩 모델을 바꾸면 얼마나 오르는지 채점표로 쟀다. 전에는 블라인드 비교로 "상위 결과가 20%만 겹친다"까지만 봤었다.

## 방법
- 3시점(7/1·8/1·9/1) × 회사 300곳, 정답=낙찰(마감 2일 이상), 운영 파이프라인 그대로(hybrid 업종 채널, pool 200, 점수표 현재).
- 모델별로 **활성 공고 + 표본 회사의 이력 공고 + 업종 텍스트**를 같은 텍스트(`embed_bid_notices.build_text`, `build_industry_text`)로 임베딩해 하네스 `--embeddings` 로 교체. 회사 벡터 합성·점수·MMR 은 동일.
- 임베딩: 노트북 GPU(RTX 5060), fp16, max_seq 512, 정규화. 시점당 ~9.5천 텍스트, 모델당 30초.
- 스크립트: `scripts/export_embed_texts.py`(텍스트 추출, backend env) → `scripts/embed_local.py`(torch env) → `jobs.evaluate_recommender --embeddings x.npz`.

## 해석
- **KURE-v1 이 후보 회수를 +0.08(0.55→0.63), 최종을 +0.04 올린다.** 세 시점 모두 dense 상승, 최종은 7/1 +0.016, 8/1 +0.037, 9/1 +0.075. rich·공사·용역은 전 시점 상승. 7/1 small(0.340→0.305)·물품(0.282→0.264), 8/1 MRR(0.213→0.188)은 하락 — 회사 3~4곳 수준.
- BGE-M3 도 OpenAI 보다 낫지만 KURE 가 한국어 특화(bge-m3 기반 한국어 미세조정)라 더 낫다.
- 점수표는 OpenAI 유사도 분포에 맞춰 보정한 것이라, KURE 로 바꾼 뒤 점수표를 다시 맞추면 더 오를 여지가 있다(유사도 척도가 다름).
- 임베딩 텍스트는 그대로(제목·업무구분·허용업종·품목분류·규격·수요기관). 문서 요약을 섞지 않은 것도 동일.

## 전환하면 드는 품 (결정 대기)
1. 벡터 컬럼 1024d 신설(bid_notices·companies·pre_specs·order_plans) + 인덱스, RPC 차원 변경.
2. 재임베딩: 활성 공고 ~1만 + 매일 신규 ~1.5천, 회사 7.8만(업종 텍스트), 사전규격·발주계획. GPU PC 에서 1~2시간, 이후 매일 잡.
3. 서빙: 회사 모드는 벡터가 미리 계산돼 모델이 필요 없다. **키워드 모드 질의 임베딩**만 실시간 — (a) Railway CPU 에 ONNX int8 로 싣기(~300ms, 메모리 1GB), (b) Modal 같은 서버리스 GPU, (c) 호스팅 API 는 KURE 가 없어 bge-m3 로 타협. (a) 가 가장 단순.
4. 채점표 재보정(점수표) 후 전후 비교 → 배포. 롤백은 컬럼 스위치.

## 부록: ONNX int8 양자화 손실 (2026-10-15, 전환 Task 1)

CPU 서빙용(Railway 요청 시점·Actions 배치) ONNX int8 을 만들려 했으나 **dynamic int8 은 계획의 합격선
(fp16 GPU 임베딩 대비 코사인 평균 ≥ 0.995, 최소 ≥ 0.98)을 어떤 변형으로도 못 넘는다.**
`docs/recommender/scripts/export_kure_onnx.py [out] [variant]` 로 재현. 비교 200건 = `texts-2026-08-01.json` 공고 텍스트,
pooling CLS + L2(= 모델의 `1_Pooling/config.json`), max_len 512.

| variant | 파일 | 코사인 평균 | 최소 | 1문장 지연(16코어 CPU, 4스레드) |
|---|---|---|---|---|
| fp32 (양자화 없음) | 2,267MB | 1.00000 | 1.00000 | 160 ms |
| `ffn-pc` attention 제외 FFN MatMul per-channel | 1,664MB | 0.99149 | 0.98985 | — |
| `mm-pc` MatMul per-channel QInt8 | 1,363MB | 0.98507 | 0.98068 | 45 ms |
| `mm` MatMul per-tensor QInt8 | 1,362MB | 0.97723 | 0.97157 | — |
| `all` 전 op QInt8(임베딩 Gather 포함) | 569MB | 0.97741 | 0.97092 | 25 ms |

- fp32 ONNX 는 fp16 GPU 와 코사인 1.00000 — export·pooling·tokenizer 는 정확하다. 손실은 전부 양자화에서 온다.
- 임베딩 행렬(250k×1024)을 양자화하면 0.977 로 떨어지고, 거기서 빼면 파일이 1.36GB 로 커진다(계획이 가정한 ~560MB 불가).
- per-channel 이 per-tensor 대비 +0.008. QUInt8 가중치(0.98485)·`reduce_range`(0.98198)는 개선 없음.
- **결정 필요**: ① 합격선을 완화(0.985 가 실제 추천 품질을 얼마나 깎는지는 하네스 `--space kure` 로 재서빙 비교해야 안다)
  ② fp16 ONNX(1.13GB, 코사인 ~1.0, 단 ORT CPU fp16 은 fp32 로 캐스팅해 느림) ③ 요청 시점만 GPU 서버리스(Modal).

### 후보 회수 영향 — int8 채택 근거 (2026-10-15)

코사인 0.977 이 실제 후보 집합을 얼마나 바꾸는지 직접 쟀다. 질의 = `texts-2026-08-01.json` 업종 텍스트 50건,
문서 = 같은 파일 공고 9,707건(`kure-2026-08-01.npz`, fp16 GPU = fp32 와 코사인 1.0), 질의 벡터만 fp32 ONNX vs int8 ONNX.

| 지표 | 값 |
|---|---|
| 질의 코사인 (fp32 vs int8) | 평균 0.97684 / 최소 0.96981 |
| **top-100 후보 중복** | **평균 0.8684** / 최소 0.7800 / p5 0.7900 |
| top-10 중복 | 평균 0.8020 |
| top-100 구성원 평균 순위 이동 | 16.7위 (최대 31.5) |

→ 합격선 0.85 통과. **서빙(Railway 요청 시점)은 569MB int8(zip 409MB, 20~25ms/문장) 채택.**
매일 배치·GPU 백필은 양자화 손실을 안 쓸 이유가 없어 sentence-transformers 원본(`KURE_BACKEND=torch`,
`uv sync --extra embed-cpu`)으로 간다. 두 백엔드 동일 3문장 코사인 0.980~0.983 (`x` 같은 1글자 입력은 0.978).
