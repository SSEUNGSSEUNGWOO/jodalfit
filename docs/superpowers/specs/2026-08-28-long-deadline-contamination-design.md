# 장기마감 공고 오염 제거 — 설계

작성 2026-08-28

## 문제

회사 페이지(`/companies/[bizrno]`)의 추천 TOP이 실제 투찰 가능한 공고가 아니라
마감이 수년 뒤인 단가계약성 공고로 채워진다.

실측 (2026-08-28):

| 회사 | TOP 20 중 장기 | TOP 5 중 장기 |
| --- | ---: | ---: |
| 삼성에스디에스 주식회사 | 12/20 | 4/5 |
| 주식회사 만평산업 | 20/20 | 5/5 |

삼성에스디에스 페이지 1~12위가 *사무환경기기임대서비스, 안마의자임대서비스,
제설장비임대서비스, 번역서비스*이고, 실제로 맞는 공고(긴급신고통합시스템 기능개선,
AI시스템 구축 용역, 사이버보안 기본계획 수립)는 13위 아래로 밀렸다.

## 원인

`match_bid_notices`의 필터가 `bid_clse_date >= today` 하한뿐이라 상한이 없다.
마감이 수년 뒤인 공고는 이 필터를 **영구히** 통과하며 모든 회사의 후보 풀에 남는다.
`rerank`의 D-day 로직도 `6~14일` 가점과 `≤1일` 감점만 있어 D+1394에는 아무 처리가 없다.

활성 공고(임베딩 보유)의 마감까지 일수 분포:

```
D+0~7      6,072      D+60~90        5   ← 절벽
D+7~14     2,268      D+90~180      17
D+14~30      720      D+180~365     39
D+30~60      209      D+365~10년   249
                      D+10년~      115
```

D+180 초과 200건 표본: 발주기관 **조달청 181건**, 업무구분 **물품 170건**.
공고명은 흙콘크리트·전선관·아스팔트콘크리트·화장지·난방패널 등 — 조달청 종합쇼핑몰
단가계약(다수공급자계약) 품목이다. "마감 전에 검토해 투찰하는 공고"와 성격이 다르다.

`bidwinr_dcsn_mthd_nm`에 "다수공급자계약" 값이 있으나 장기 표본 150건 중 114건이
NULL이라 식별자로 쓸 수 없다. **마감일 경계가 가장 신뢰할 수 있는 신호**다.

## 수정 위치 — RPC여야 하는 이유

후보 풀(RPC top-200) 오염률 실측:

| 회사 | top-20 | top-50 | top-200 | D+90 내 잔존 |
| --- | ---: | ---: | ---: | ---: |
| 삼성에스디에스 | 6/20 | 11/50 | 23/200 | 177건 |
| 주식회사 만평산업 | 19/20 | 46/50 | **169/200** | **31건** |

만평산업은 RPC가 돌려준 200건 중 169건이 장기라, Python에서 후처리로 걸러내면
후보가 31건으로 쪼그라들어 `candidate_pool=100`을 못 채운다. 그러면 v2 랭커가
고를 것이 없다. 따라서 **RPC 단계에서 걸러야** 한다.

## 설계

### 마이그레이션 `0018_match_bid_notices_max_horizon.sql`

`match_bid_notices`에 `max_clse_date date default null`을 추가하고, 0016의
materialized CTE 안에 조건 한 줄을 더한다:

```sql
and (max_clse_date is null or b.bid_clse_date <= max_clse_date)
```

0016의 "필터 먼저 → 정확 top-N 정렬" 플랜은 그대로 유지된다. `active` CTE가
작아지므로 성능은 같거나 조금 낫다.

**반드시 `drop function` 후 `create`한다.** `create or replace`로 파라미터만
추가하면 arity가 달라 새 오버로드가 생기고, 인자 4개 이하 호출이 두 함수 사이에서
모호해져 `function is not unique`로 깨진다. 이 저장소의 `0011_drop_old_match_pre_specs.sql`이
같은 문제를 처리한 선례다.

적용 순서는 어느 쪽이든 안전하다:
- 마이그레이션 먼저 → 구버전 코드의 4-arg 호출도 단일 함수의 default로 정상 해석된다.
- 배포 먼저 → 신버전의 5-arg 호출이 `PGRST202`를 받고 아래 폴백으로 degrade한다.

### `backend/app/services/recommend.py`

- 상수 `MAX_CLSE_HORIZON_DAYS = 90`.
  D+60~90 구간의 활성 공고가 5건뿐이라 경계 위치에 민감하지 않고, 90은 여유값이다.
- `_search_with_embedding`이 `max_clse_date = today + 90일`을 넘겨 호출한다.
- **폴백**: 마이그레이션 미적용 시 `PGRST202`가 나므로 잡아서 4-arg로 재호출하고
  Python에서 같은 조건으로 거른다. 미적용 환경에서도 죽지 않게 하는 `0015` RPC 패턴과 같다.
  degrade 상태에선 만평산업 후보가 31건으로 줄지만, 현재의 20/20 오염보다는 낫다.

### 적용 범위

입찰공고(`match_bid_notices`)만. 사전규격은 의견마감 D+180 초과가 **0건**으로 측정돼
해당 없고, 발주계획은 애초에 미래 계획이라 성격이 다르다.

`/notices` 브라우즈 페이지에도 같은 공고가 섞여 있으나 사용자가 필터를 직접 거는
화면이라 이번 범위에서 제외한다.

## 검증

1. 삼성에스디에스·만평산업 TOP 20에 D+90 초과 **0건**
2. 두 회사 모두 필터 후 후보 풀 **100건 이상** 확보
3. 폴백 경로: 5-arg 호출이 `PGRST202`일 때 4-arg + Python 필터로 같은 결과
4. 다른 에러코드는 폴백 없이 그대로 전파
5. 기존 추천 회귀 없음 (결과 건수·회사 식별)
6. 육안 확인: 추천 상위가 실제 투찰 가능한 공고로 바뀌었는지

## 이 수정이 여는 후속 작업

캐시(`company_recommendations` read-through) 설계가 이 수정에 막혀 있었다.
지금은 TOP 20 중 12~20건이 마감 수년 뒤라 "살아있는 결과가 N건 미만이면 재계산"이라는
내용 기반 무효화가 **영원히 발동하지 않는다**. 이 수정 후에는 남는 공고의 마감이
3~20일 범위라 캐시가 2~3주면 자연 감쇠하고, 시계 기반 TTL 없이 내용 기반 무효화만으로
충분해진다.
