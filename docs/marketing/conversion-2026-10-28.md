# 결과에서 저장으로 이어지는 흐름 (2026-10-28)

## 화면

- 회사 추천·키워드 글자 일치 목록에 저장 버튼을 항상 노출한다. 펼침과 저장은 별개 동작이며 비로그인은 기존 로그인 복귀 URL을 유지한다.
- 제목으로 공고 상세를 여는 동작도 공고 클릭으로 기록한다.
- 저장 성공 뒤에만 저장 이벤트를 한 번 보낸다. 실패·해제·이미 저장된 행(23505)은 새 저장으로 세지 않는다. 오류 시 버튼에 다시 시도를 표시한다.

## /admin의 결과 이후 전환

오늘과 오늘 포함 7일을 한국 날짜로 집계한다. 브라우저 탭의 `jf_sid`를 PostHog 이벤트 `jf_session_id`로 같이 보내 같은 탭의 행동을 연결한다. 계정·이메일은 추가로 보내지 않는다.

| 이벤트 | 시점 |
| --- | --- |
| results_view | 결과가 화면에 표시됨. 동일 마운트에서 1회, 브라우저 캐시 결과 포함 |
| notice_click | 공고 행 펼침 또는 제목 클릭 |
| notice_save_intent | 비로그인의 저장→로그인 이동, 또는 로그인 사용자의 저장 시도. logged_in 0/1 |
| notice_save | DB insert 성공 뒤 1회 |
| signup_view | 가입 화면 진입. 가입 완료가 아님 |

결과 조회 이후 행동만 탭마다 한 번 센다. 공고 열기와 저장 시도는 각각 결과 조회 대비다. 저장 성공률은 저장 시도 대비이고, 가입 화면 진입률은 비로그인 저장 시도 대비다. 공고를 열지 않고 직접 저장해도 집계된다. 같은 기간의 서로 다른 사용자를 나눠 전환율로 오해하지 않도록 기존 DB 기반 활동 건수와 판을 분리했다.

내부 SSR은 클라이언트 이벤트를 만들지 않는다. 로컬 주소·알려진 봇은 새 클라이언트 계측에서 제외하며, 집계 쿼리는 운영 도메인만 읽는다. 백엔드 `/events`도 요청 출처를 서버에서 판정해 기록한다.

## 설정·한계

- 기존 `NEXT_PUBLIC_POSTHOG_KEY` / `POSTHOG_PERSONAL_API_KEY` / `POSTHOG_PROJECT_ID`를 사용한다. DB 마이그레이션은 없다.
- 새 세션 속성이 있는 이벤트만 읽으므로 배포 후부터 누적된다. 조회 키가 없거나 API가 실패하면 0 대신 조회 불가를 표시한다.
- 최근 7일 이벤트 10,000건을 넘으면 일부 이벤트라는 경고를 표시한다. 계측 차단·다른 탭·다른 기기로 이동하면 흐름이 끊길 수 있다.
- 가입 **완료**와 7일 **재방문**을 이 판의 전환으로 연결하지 않는다. 가입자 및 인증 상태는 기존 Auth 판에서 확인한다.

검증: 순수 집계 단위 테스트, 실제 PostHog API 쿼리 200, `scripts/check_result_actions.py`의 모의 스트림으로 1280/390 UI·제목 클릭 1회·복귀 URL·게이트 inert 확인. 별도 임시 화면으로 저장 성공·해제·실패·중복과 관리자 판의 정상·조회 불가 상태를 검증하고 임시 화면은 제거했다.

프론트 단위 검사 30개·백엔드 회귀 검사 10개 통과. lint는 오류 0개(기존 미사용 함수 경고 2개). production build 통과. 로컬에는 Supabase 공개 인증 키가 없어 UI·빌드 검증에는 가짜 공개 URL/키를 프로세스 환경변수로만 넣었으며, 실제 회원가입이나 운영 DB 저장은 수행하지 않았다. 관리자 권한·실제 로그인까지 포함하는 전체 `check_admin.py`는 실행하지 않았다.
